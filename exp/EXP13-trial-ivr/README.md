# EXP13 — Trial IVR: constructive re-derivation of published GGUF quants

**Question.** For real, popularity-sampled GGUF releases, is the published quantized file *independently
re-derivable bit-for-bit*, and if not, exactly which coordinates absent from the model card close the gap?
This turns the ecosystem-level `IVR = 0/198` under the recorded-inputs protocol (EXP03) into a controlled, constructive experiment on named
artifacts, and replaces the single best-case attempt of EXP09 (n=1, the 1.5B) with a grid over four
published targets, two model families / architectures, and a matrix of build environments.

## Targets (in-sample; each ships its own inputs)

All four are among the 200 most-downloaded GGUF repositories (EXP03 census) and publish, in one repo, the
full-precision GGUF we quantize from, the imatrix used, and the `Q4_K_M` and `Q8_0` files we compare to.
The model card of each states the `llama.cpp` release used for quantization; we build exactly that release.

| repo | family / arch | card release | tensors |
|---|---|---|---|
| `bartowski/Qwen2.5-7B-Instruct-GGUF` | Qwen2.5, dense transformer | **b3772** | 339 |
| `bartowski/Qwen_Qwen3.5-0.8B-GGUF` | Qwen3.5, hybrid (SSM+attn) | **b9222** | 335 |
| `bartowski/Qwen_Qwen3.5-2B-GGUF` | Qwen3.5, hybrid | **b9222** | 335 |
| `bartowski/Qwen_Qwen3.5-4B-GGUF` | Qwen3.5, hybrid | **b9222** | 441 |

The card text is quoted verbatim in `data/cards.md` (e.g. *"Using llama.cpp release b9222 for quantization.
All quants made using imatrix option …"*). No card states any build-environment coordinate (compiler,
architecture, FP-contraction) or the per-tensor quantization recipe.

## Method

For each target we re-quantize the publisher's own full-precision GGUF to `Q4_K_M` (with the published
imatrix) and to `Q8_0`, in each build environment, in two modes, and compare **per-tensor sha256 of the
tensor data** to the published file (`tools/gguf_tensor_shas.py`, stdlib-only; per-tensor byte ranges are
taken from consecutive GGUF data offsets, so no ggml type-size table is needed).

- **plain** — the card's information only: the stated release, the published imatrix, and the stock
  `Q4_K_M` / `Q8_0` preset.
- **recipe** — plain, plus the published file's exact per-tensor type map, pinned via
  `llama-quantize --tensor-type-file` (generated by `mkrecipe.py` from the published file). This makes the
  *quantization recipe* an explicit, supplied coordinate rather than a hidden one; the re-derivation then
  differs from the published file only through the build environment. (Available from the b9222 line;
  the older b3772 `llama-quantize` has no `--tensor-type` flag, but the 7B needs no recipe — see below.)

Build environments (`build_llama.sh` builds `build-default` and a `build-ffpoff` that appends
`-ffp-contract=off` to `ggml-quants.c`, i.e. PR #25353):

- `armclang` — Apple clang 21.0.0 (clang-2100.1.1.101) on arm64 (macOS 26, Apple M4 Pro).
- `armgcc15` — Homebrew GCC 15.2.0 (`gcc-15`) on arm64 (b3772 only; gcc-15 cannot compile the b9222 tree against the
  macOS 26 SDK, so this environment is absent for the Qwen3.5 family).
- `x86gcc` — gcc 13.3.0 on x86-64 (Ubuntu 24.04; Intel Core i5-9600KF: AVX2+FMA, no AVX-512).

Each environment is run with FP contraction on (`default`) and off (`ffpoff`). `|A|` build configurations:
6 for the 7B, 4 for each Qwen3.5 target.

## Result — the file is reproducible, but only with card-absent coordinates

Re-derivation using **the card's information alone (release + imatrix + stock preset, default build)**
reproduces **no Q4_K_M file**, and only a minority of their tensors (the one file that does reproduce from the card alone is the dense 7B's Q8_0, whose stock preset equals the publisher's recipe):

- Qwen3.5 `Q4_K_M`: 140/335 (0.8B, 2B), 184/441 (4B).
- 7B `Q4_K_M`: 141/339.

Supplying the missing coordinates closes the gap for **7/8** (target × quant) pairs on x86 (**5/8** on arm64, see †), and *which* coordinates
are missing depends on the model. On the publisher's own architecture (x86) the numbers below are, per
condition, the tensor-match / total (`*` = full bit-exact); the `+FP-flag` column is arm64.

| target / quant | card-only (arm64 dflt) | +recipe (x86 dflt) | +recipe +FP-flag (arm64) | reproduces? |
|---|---|---|---|---|
| Qwen3.5-0.8B `Q4_K_M` (hybrid) | 140/335 | **335/335\*** | **335/335\*** | ✓ |
| Qwen3.5-2B `Q4_K_M` (hybrid) | 140/335 | **335/335\*** | **335/335\*** | ✓ |
| Qwen3.5-4B `Q4_K_M` (hybrid) | 184/441 | **441/441\*** | **441/441\*** | ✓ |
| Qwen3.5-0.8B/2B `Q8_0` (hybrid) | 298/335 | **335/335\*** | 334/335† | ✓ (x86) |
| Qwen3.5-4B `Q8_0` (hybrid) | 393/441 | **441/441\*** | **441/441\*** | ✓ |
| Qwen2.5-7B `Q8_0` (dense) | **339/339\*** | — (preset = recipe) | — | ✓ (card only) |
| Qwen2.5-7B `Q4_K_M` (dense) | 141/339 | 170/339 (x86, best) | 141/339 | ✗ (no config bit-exact) |

**23 of 60** (target × quant × environment) attempts are fully bit-exact; the reproducing conditions are the
point:

- **Recipe is the key coordinate.** For the hybrid Qwen3.5 models the stock `Q4_K_M`/`Q8_0` preset does not
  reproduce the publisher's per-tensor type map (it keeps `ssm_alpha`/`ssm_beta` at F32 and bumps others to
  Q5_K/Q6_K/Q8_0, differing on 75/335 and 100/441 tensors). The card records only "Q4_K_M". Pinning the
  published recipe via `--tensor-type-file` (b9222 line only; b3772 has no such flag) closes it. For the dense
  7B the stock preset already equals the publisher's recipe (types 339/339), so no recipe is needed.
- **FP contraction is the second coordinate, and it is architecture-conditioned.** With the recipe pinned,
  the Qwen3.5 `Q4_K_M` re-derives **bit-for-bit on x86 (both default and `-ffp-contract=off`) and on arm64
  with `-ffp-contract=off`**, but **not** on an arm64 *default* build (193/335). At b9222 the ggml quant
  kernels are portable (no `-march=native`), so baseline x86-64 — which has no FMA instruction — is
  *uncontracted for free*, whereas arm64 (NEON always has FMA; clang contracts by default) needs PR #25353's
  flag. Once contraction is off, the output is **bit-identical across x86 and arm64**. So a same-architecture
  (x86) verifier needs only the recipe; a cross-architecture (arm64) verifier additionally needs the FP flag.
- **†** The one residual on the arm64 `Q8_0` path (0.8B/2B) is `blk.0.attn_qkv.weight`, which has all-zero
  weight blocks: a zero block has scale 0 and dequantizes to 0 regardless of the stored int8 codes, and the
  arm64 and x86 kernels store different `round(0/0)` codes there. **Byte-different but numerically identical**
  — bit-exactness is strictly stronger than numerical equality. On x86 (the publisher's architecture) this
  tensor matches and the file is fully bit-exact.
- **The 7B does not reproduce in any of the six build configurations** (best 170/339, x86 default). Its
  release **b3772** compiles `ggml-quants.c` with `-march=native`, so the k-quant path additionally depends on the host's SIMD ISA (AVX2 vs AVX-512 vs NEON); none of our six configurations reproduced the file, and we did not identify the publisher's environment (a different compiler version or build host may add further coordinates). The environment coordinate is therefore *larger* for this older release —
  a useful contrast with the b9222 targets, whose portable kernels reduce the environment to FP contraction.

## Takeaway

The published artifacts are **not** independently re-derivable from what their model cards disclose, but they *are* (except for the b3772 `Q4_K_M`) re-derivable once two small, discrete, publishable coordinates are supplied — the build's
FP-contraction setting and (for hybrid models) the per-tensor quantization recipe — neither of which is the
weight data. This is the verifiability gap made constructive: it names exactly what a model card or the GGUF
format would need to record for `Q4_K_M`/`Q8_0` releases to become independently verifiable, and shows the
disclosure needed for a *recent* release is small (a build flag plus a few hundred type labels). Two caveats the paper states: an older release (b3772, `-march=native`) additionally pins the SIMD ISA and was not reproduced in any of our six configurations, and the imatrix must be shipped and hash-bound rather than recomputed (EXP16).

## Files

- `scripts/fetch.sh` — download the targets' inputs (and, with `WITH_PUBLISHED=1`, the published files).
- `scripts/quantize_compare.sh` — re-quantize per environment in plain/recipe modes, record per-tensor sha.
- `scripts/mkrecipe.py` — build a `--tensor-type-file` pinning every tensor to its published type.
- `scripts/aggregate.py` — per-tensor comparison, bit-exact rate with Wilson CI, `|A|`.
- `scripts/summarize.py` — the reproduction matrix and minimal-coordinate table above.
- `data/index.csv`, `data/summary.md`, `data/cards.md` — the recorded shas index, the printed summary, the
  quoted card text. Large `.gguf` outputs are hashed and deleted; only the sha JSONs are kept.

## EXP13b — all 23 published quant types of one repository (`data/alltypes_0.8B/`)

To show the recipe gap is not specific to `Q4_K_M`/`Q8_0`, we re-derived **every** quantized file the
Qwen3.5-0.8B repository publishes — 23 types spanning k-quants (`Q2_K`…`Q6_K`, `_S/_M/_L/_XL`), legacy
quants (`Q4_0`, `Q4_1`), i-quants (`IQ2_M`, `IQ3_XXS/XS/M`, `IQ4_XS/NL`), and the publisher's
embed/output-override variants — from the repo's own bf16 + imatrix at the stated release `b9222`, in the
`plain` (card-only) and `recipe` (published type map pinned) modes, on x86 in both build variants
(`scripts/alltypes.sh`, `alltypes_summary.py`).

| | card-only (stock preset) | + published recipe |
|---|---|---|
| bit-exact re-derivations | **0/23** | **23/23** |

From the card's information alone (the named type + imatrix + release), **no** type reproduces — the stock
preset matches only 248–299 of 335 tensors, and the very-low-bit i-quants do not even complete, because the
publisher keeps the hybrid model's MTP/SSM tensors at `Q8_0`/`F32` where the stock low-bit preset would
demand an (absent) imatrix entry. Supplying the published per-tensor type map re-derives **all 23** files
bit-for-bit (both build variants, since x86 is uncontracted). The per-tensor recipe is thus a hidden
coordinate for the publisher's entire quantization lineup, not just the two headline types.
